1) What Docker Is Actually Useful For

At a practical level, Docker helps you package an application together with its runtime dependencies and startup instructions so that the same artifact can run more consistently in development, CI, test, and production-like environments.

  • Local development environments that are easier to reproduce
  • Isolated test environments per branch or PR
  • Packaging internal services and utilities
  • Standardizing build and deploy artifacts
  • Moving workloads into orchestrators such as Kubernetes
  • Reducing "works on my machine" drift between team members

2) Docker Installation Explained

Docker Desktop

For most developers on macOS, Windows, or Linux workstations, Docker Desktop is the normal starting point — a one-click install application that lets you build, share, and run containerized applications.

💡

Licensing note: Docker Desktop commercial use in organizations with more than 250 employees or more than $10 million in annual revenue requires a paid subscription.

⚠️

On Windows with WSL 2, do not install Docker Engine inside WSL and also run Docker Desktop — this causes conflicts. Use WSL 2.1.5+ for best results.

Docker Engine

Docker Engine is the lower-level daemon/runtime stack commonly used on Linux servers and cloud VMs — no Desktop UI, leaner, and with direct host-level control.

bash — Linux post-install 
# Add current user to the docker group (avoid sudo)
sudo usermod -aG docker $USER
newgrp docker

# Enable Docker to start at boot
sudo systemctl enable docker.service
sudo systemctl enable containerd.service

# Verify installation
docker version
docker info

3) Core Docker Concepts

Image Packaged read-only template (layers) Dockerfile, build context, cache

daemon (dockerd) Background service that manages container lifecycle daemon.json, system resources, socket permissions

4) Running Images and Containers

bash — day-to-day workflow 
# Verify Docker works
docker version
docker info
docker run hello-world

# Pull an image
docker pull nginx:latest

# Run a named container with port mapping (-d = detach)
docker run -d --name web -p 8080:80 nginx:latest

# Inspect running containers
docker ps
docker ps -a          # include stopped containers

# Follow logs and get a shell
docker logs -f web
docker exec -it web sh

# Stop and clean up
docker stop web
docker rm web

Running Containers with Resource Limits

By default a container has no resource constraints and can use as much CPU or memory as the host scheduler allows. Always set limits for production-like and shared environments:

bash — resource-constrained container 
docker run -d \
  --name api \
  --memory="512m" \
  --cpus="1.5" \
  --restart unless-stopped \
  -p 3000:3000 \
  -e NODE_ENV=production \
  my-api:1.0

5) Docker Runtime Selection

✅

Practical default: For normal development, CI, and standard Linux server workloads, stick with the default Docker runtime. Runtime complexity rarely adds value for ordinary application teams.

Runtime choice becomes important for:

  • Higher isolation requirements (e.g., gVisor, Kata)
  • Special node-level sandboxing in regulated environments
  • Kubernetes RuntimeClass multi-runtime clusters
  • Platform engineering work at the node level

7) Managing Docker Configuration Through Files

The JSON configuration file (daemon.json) is the preferred option because it keeps settings in one place. Do not specify the same option both as a flag and in the JSON file — this prevents the daemon from starting.

daemon.json

json — /etc/docker/daemon.json 
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  },
  "builder": {
    "gc": {
      "enabled": true,
      "defaultKeepStorage": "20GB"
    }
  },
  "live-restore": true
}

Proxy Configuration

json — daemon proxy settings 
{
  "proxies": {
    "http-proxy":  "http://proxy.example.com:3128",
    "https-proxy": "http://proxy.example.com:3128",
    "no-proxy":    "localhost,127.0.0.1,.internal.example.com"
  }
}

8) Docker Image Cleanup and Disk Management

Docker takes a conservative approach to removing unused resources — they are not removed unless you ask. Disk usage grows over time without periodic pruning.

bash — cleanup commands 
# Check disk usage first
docker system df

# Prune in layers (safest approach)
docker container prune     # stopped containers
docker image prune         # dangling images only
docker image prune -a      # all unused images
docker network prune       # unused networks
docker builder prune       # build cache

# Full nuke (add --volumes only when safe)
docker system prune -a
docker system prune -a --volumes
⚠️

Never run docker volume prune blindly — local databases (Postgres, MySQL, etc.) live in volumes. Pruning them deletes all local data permanently.

9) Docker Best Practices That Actually Matter

Use Multi-Stage Builds

Multi-stage builds keep build tools out of runtime images, resulting in smaller, cleaner, and more secure final images. This is the single highest-value Dockerfile improvement most teams can make.

Dockerfile Samples

dockerfile — Node.js multi-stage 
# ── Stage 1: install dependencies ────────────────────────────────
FROM node:20-alpine AS deps
WORKDIR /app
RUN npm install -g pnpm
COPY package.json pnpm-lock.yaml* ./
RUN pnpm install --frozen-lockfile

# ── Stage 2: build ───────────────────────────────────────────────
FROM deps AS build
COPY . .
ENV NODE_ENV=production
RUN pnpm build && pnpm prune --prod

# ── Stage 3: lean runtime image ──────────────────────────────────
FROM node:20-alpine AS runtime
WORKDIR /app
ENV NODE_ENV=production

# Non-root user for security
RUN addgroup --system --gid 1001 nodejs \
 && adduser  --system --uid 1001 appuser

COPY --from=build --chown=appuser:nodejs /app/dist        ./dist
COPY --from=build --chown=appuser:nodejs /app/node_modules ./node_modules
COPY --from=build --chown=appuser:nodejs /app/package.json ./

USER appuser
EXPOSE 3000
CMD ["node", "dist/main.js"]
dockerfile — Go multi-stage 
# ── Stage 1: build Go binary ─────────────────────────────────────
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /bin/server ./cmd/server

# ── Stage 2: minimal runtime (distroless) ────────────────────────
FROM gcr.io/distroless/static-debian12
COPY --from=builder /bin/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]
dockerfile — Python FastAPI 
# ── Stage 1: dependency builder ──────────────────────────────────
FROM python:3.12-slim AS builder
WORKDIR /app
RUN pip install --no-cache-dir poetry==1.8.3
COPY pyproject.toml poetry.lock ./
RUN poetry config virtualenvs.in-project true \
 && poetry install --only main --no-interaction

# ── Stage 2: runtime ─────────────────────────────────────────────
FROM python:3.12-slim AS runtime
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1

COPY --from=builder /app/.venv /app/.venv
COPY src/ ./src/

ENV PATH="/app/.venv/bin:$PATH"
EXPOSE 8000
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]

10) Docker Compose — Multi-Container Apps

Docker Compose is the standard tool for defining and running multi-container applications locally. A single compose.yaml file replaces many docker run commands.

yaml — compose.yaml (full-stack app) 
name: myapp

services:

  api:                           # Node.js / Go / Python backend
    build:
      context: ./backend
      target: runtime             # multi-stage target
    image: myapp/api:local
    restart: unless-stopped
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: production
      DATABASE_URL: postgres://app:secret@db:5432/appdb
      REDIS_URL: redis://cache:6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: 512M

  frontend:                      # Angular / Next.js / React
    build:
      context: ./frontend
      target: runtime
    ports:
      - "8080:80"
    depends_on:
      - api

  db:
    image: postgres:16-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 10s
      retries: 5

  cache:
    image: redis:7-alpine
    restart: unless-stopped
    command: redis-server --save 60 1 --loglevel warning

volumes:
  pgdata:
bash — Compose workflow 
# Start everything (build first if needed)
docker compose up -d --build

# Follow logs for all services
docker compose logs -f

# Scale a service
docker compose up -d --scale api=3

# Stop without removing volumes
docker compose stop

# Full teardown including volumes
docker compose down -v

12) Docker and Kubernetes: The Correct Modern Explanation

Modern Kubernetes expects a CRI-compatible runtime on each node. The built-in dockershim was removed. Docker-built images continue to work — the issue was the runtime interface, not the image format.

☸️

Key takeaway: Application developers usually define image, env, ports, resources, and probes. Kubernetes runs those Pods using whatever CRI runtime the cluster nodes are configured with — you don't need to specify containerd or similar in daily workloads.

Kubernetes Deployment

yaml — k8s Deployment 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-deployment
  labels:
    app: api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
        - name: api
          image: myapp/api:1.0.0
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 3000
          env:
            - name: NODE_ENV
              value: production
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: app-secrets
                  key: database-url
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1"
              memory: "512Mi"
          livenessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 15
            periodSeconds: 20
          readinessProbe:
            httpGet:
              path: /ready
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10

Pod Configuration Reference

yaml — Pod spec with security context & volumes 
apiVersion: v1
kind: Pod
metadata:
  name: api-pod
  labels:
    app: api
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1001
    fsGroup: 1001

  volumes:
    - name: app-config
      configMap:
        name: api-config
    - name: tmp-volume
      emptyDir: {}

  containers:
    - name: api
      image: myapp/api:1.0.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      ports:
        - containerPort: 3000
      volumeMounts:
        - name: app-config
          mountPath: /app/config
          readOnly: true
        - name: tmp-volume
          mountPath: /tmp
      resources:
        requests:
          memory: "128Mi"
          cpu: "100m"
        limits:
          memory: "256Mi"
          cpu: "500m"

Init Containers

Init containers run and complete before the main application container starts. Common uses: wait for a database, migrate schemas, fetch secrets, or pre-populate caches.

yaml — Pod with init containers 
apiVersion: v1
kind: Pod
metadata:
  name: api-with-init
spec:

  initContainers:

    # 1. Wait for the database to be ready
    - name: wait-for-db
      image: busybox:1.36
      command:
        - sh
        - -c
        - |
          until nc -z db-service 5432; do
            echo "waiting for postgres..."; sleep 2;
          done
          echo "postgres is up"

    # 2. Run database migrations
    - name: db-migrate
      image: myapp/api:1.0.0
      command: ["node", "dist/migrate.js"]
      env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: app-secrets
              key: database-url

    # 3. Fetch external configuration / secrets
    - name: fetch-config
      image: curlimages/curl:8.5.0
      command:
        - sh
        - -c
        - |
          curl -sS https://config-service/api/config \
            -H "Authorization: Bearer $TOKEN" \
            -o /shared/app.json
      volumeMounts:
        - name: shared-config
          mountPath: /shared

  containers:
    - name: api
      image: myapp/api:1.0.0
      ports:
        - containerPort: 3000
      volumeMounts:
        - name: shared-config
          mountPath: /app/config

  volumes:
    - name: shared-config
      emptyDir: {}

RuntimeClass — Choosing a Runtime Per Pod

yaml — RuntimeClass for sandboxed workloads 
# Define the RuntimeClass (cluster admin task)
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor
handler: runsc

---
# Reference it in a Pod (workload owner task)
apiVersion: v1
kind: Pod
metadata:
  name: sandboxed-api
spec:
  runtimeClassName: gvisor  # ← select the runtime
  containers:
    - name: api
      image: myapp/api:1.0.0
☸️

RuntimeClass is a platform-level concern, not a daily application task. Most teams never need to set runtimeClassName — they rely on the cluster default.

13) Docker Desktop and Local Kubernetes

Docker Desktop can spin up a local Kubernetes cluster (single-node kubeadm or kind-based multi-node), making it ideal for learning Pods, Services, Deployments, and Ingress — and for validating Helm charts or Kustomize flows before pushing to CI.

bash — quick local Kubernetes test 
# Check context
kubectl config current-context   # should show docker-desktop

# Apply a deployment manifest
kubectl apply -f k8s/deployment.yaml

# Watch rollout
kubectl rollout status deployment/api-deployment

# Port-forward for local access
kubectl port-forward deployment/api-deployment 3000:3000

# Inspect events on failure
kubectl describe pod -l app=api
kubectl logs -l app=api --tail=50

Final Practical View

The biggest Docker maturity gains come from a small set of consistent habits — not advanced runtime tricks:

  • Standard, reproducible Dockerfiles with multi-stage builds
  • Sensible CPU and memory limits on every container
  • Daemon-level logging rotation and cache garbage collection
  • Repeatable local Compose stacks for every service
  • Disciplined image refresh (--pull, --no-cache) and periodic pruning
  • Clear separation between developer concerns and platform/runtime concerns
